## 2. الخلل الماصود: الجلسة المنهارة والبصمة التي قارنت نفسها

جلسة سابقة كتبت `SignedDict.java` وأوقفت قبل أول تشغيل. عند تشغيل البوابة
الجديدة **رفض الأصل المشحون نفسه بوسم PIN** — التشخيص: `verify()` قارن جسد
الكلمات المعاد تسلسله **مع** بصمة sha256 بدل مقارنة البصمتين، فأي حزمة صحيحة
كانت ستفشل. الإصلاح سطر واحد (`sha256Hex(recomputed) == bodySha256`)، والدليل
على سلامة الأصل: إعادة النشر الحتمية أنتجت **بايتات مطابقة** (packSha256
`455d31e3…`). الدرس: «وحدة لم تُشغّل = وحدة مكسورة» — البوابة صادتها في أول
تشغيل لها.

## 3. الفخّان المستقلان (كلاهما مفروض ومقاس)

1. **الدبوس — تزوير ما بعد المراجعة:** `bodySha256` = sha256 لإعادة التسلسل
   الكانوني لمصفوفة الكلمات؛ النشر والتحقق يتقاسمان مسلسلاً واحداً. قلب قيمة،
   إعادة ترتيب صفوف، أو تحريف البصمة → رفض `PIN` للحزمة كاملة (3 سلبيات).
   إعادة تهريب JSON (\uXXXX) **لا تغير شيئاً**: القيم تُعاد كسرها متطابقة قبل
   الحكم — مثبت إيجابياً لا بالادعاء.
2. **إعادة الحكم — تجاوز المراجعة بدبوس معاد الحساب:** المهاجم يحسب الدبوس على
   صفوفه المسمومة بنفسه — وخساره حتمية لأن `verify` يعيد تشغيل **الحَكَم نفسه**
   (`CommunityDict.judge` — لا تنفيذ ثانٍ ولا انحراف ممكن) على كل صف: FORBIDDEN /
   DUPLICATE / BAD_LICENSE تُرفض بوسمها (3 سلبيات بدبوس معاد الحساب).

**المكررات مفصولة حسب التهديد (قرار موثق):** داخل الحزمة = رفض (توقيع مزور)؛
ضد المدونة المثبتة = SKIP عند الدمج — مدونة تنمو بين الإصدارات فلا يجوز أن تكسر
حزمة قديمة؛ الخطر في المحتوى الجديد لا المكرر.

## 4. عقد الترتيب (مثبت باختبار)

المدونة المثبتة أولاً ← الحزمة بترتيب صفوفها ثانياً ← كلمات المستخدم فوقها؛
norm-dedup «الأول يفوز»؛ كلمات الحزمة تأخذ أدنى تردد أساس (ذيل-طويل حتى
الاستخدام). البرهان على الأصول الحقيقية: `Dictionary.knows("دحين")` = true —
كلمة تشحن في الحزمة وحدها (الناشر يمنع تكرارها في المدونة).
