# عقد REST لخدمة مزامنة NeoKey — v1 (NSF1)

**الحالة:** موثق ومُنفّذ عميلياً (`SyncRestTransport.java`) — الخادم يُشغَّل على جهاز النشر
(خارج بيئة التطوير)، والعميل مُثبت ضد المحاكي النقي (`SyncServerSim`) في `SYNC_GATE` و`SYNCCLIENT_GATE`.

**المبدأ الحاكم (المبدأ الخامس + عقد الصفر-المعرفة):** الخادم يرى بايتات عشوائية لا معنى لها.
المصادقة هي فك التشفير نفسه — لا حسابات بريد، لا رموز حامل، لا كلمات سر مخزنة. كل ما
يُرسل عبر هذا العقد إما ملح عام (32 بايت) أو مغلف NSF1 (بلايتنص مشفر AES-256-GCM
ترويته موقعة AAD) أو معرفات b64url عشوائية.

## الأساس

- `base` الوحيد المسموح: `https://sync.neokey.app/v1/` — مثبت في قائمة NetGate البيضاء
  (`NetGate.ENDPOINTS`) ويفحص مرتين: قبل الدفع/السحب (بوابة القدرة `sync`) وعند كل طلب
  داخل `SyncRestTransport` (دفاع ثانٍ). أي نطاق آخر = رفض محلي بلا طلب.
- معرف الحساب: 128 بت مشتقة HKDF من عبارة المستخدم + الملح (`SyncVault.derive`) —
  b64url حصراً (`A-Za-z0-9_-`)، وأي محرف آخر يُرفض قبل الخروج للشبكة.

## نقاط النهاية

| # | الطريقة والمسار | الطلب | الاستجابة | الدلالة |
|---|---|---|---|---|
| 1 | `GET  account/{id}/salt` | — | `200` + 32B ملح \| `404` | قراءة الملح العلني لتسجيل جهاز جديد |
| 2 | `PUT  account/{id}/salt` | 32B ملح | `201` \| `409` | تسجيل حساب جديد؛ `409` إن وُجد بملح مختلف (الملح ليس سراً) |
| 3 | `GET  account/{id}/blobs` | — | `200` + مصفوفة JSON من معرفات b64url \| `404` | قائمة كتل الحساب (معرفات عشوائية بلا دلالة) |
| 4 | `GET  account/{id}/blob/{blobId}` | — | `200` + بايتات المغلف \| `404` | جلب كتلة |
| 5 | `PUT  account/{id}/blob/{blobId}` | بايتات المغلف | `201` \| `413` (سقف كتلة 8MB) \| `507` (حصة الحساب) | رفع كتلة |

- كل الأجسام **بايتات خام** (`application/octet-stream`) — لا JSON إلا في استجابة #3
  (مصفوفة سلاسل ASCII بلا أي محتوى مستخدم).
- `404` دلالتها الرمضاء: «لا شيء بعد» وليس خطأ — العميل يتعامل معها كقائمة فارغة.
- `409` في #2: العميل يقرأ الملح الموجود ويشتق منه — نفس العبارة تعطي نفس الحساب
  المستعار؛ عبارة مختلفة تفشل لاحقاً عند فك أول كتلة (`auth_failed`).

## الحصص (مطبقة على الخادم ومكررة محلياً قبل الرفع)

| الفئة | الحصة | سقف الكتلة |
|---|---|---|
| مجاني | 1MB / حساب | 8MB |
| VIP | 50MB / حساب | 8MB |

العميل يفحص الحصة قبل الختم (`SyncVault.checkQuota`)، والخادم يفرضها عند `PUT` (#5) —
الرفض الخادمي `413/507` يظهر للعميل كـ `http_413/http_507`.

## الضمانات المُثبتة (بوابتا `SYNC_GATE` و`SYNCCLIENT_GATE`)

1. **الصفر-المعرفة** على مخزون الخادم نفسه (`dump()`): بلا عربية، بلا أنواع سجلات، بلا
   JSON حالة، بلا حساب مستعار نصي؛ سحر `NSF1` عند بدايات الكتل فقط بعدد الكتل بالضبط؛
   إنتروبيا ≥ 7.5 بت/بايت (المقاس: 8.00).
2. **سلامة الكتل**: AAD يغطي الترويسة كاملة — أي تبديل بايت (ملح/نسخة/nonce/متن) يُرفض
   (`salt_mismatch` أو `auth_failed`) ولا يُعاد نص نصف-مبني أبداً.
3. **الاستعادة كل-أو-لا-شيء**: فشل أي كتلة يرفض الجلسة كاملة والسجل المحلي لا يُمس.
4. **الدمج حتمي**: آخر-كاتب-يفوز بترتيب كلي تبادلي (`merge(a,b)=merge(b,a)`) — نفس
   المدخلات على أي جهازين = نفس المخرجات بت-لطرف.

## ما لا يفعله العقد (مقاصد صريحة)

- لا يرى الخادم أي محتوى: إعدادات، كلمات، عبارات، تثبيتات — كلها داخل المغلف المشفر.
- لا يسجل الخادم عناوين IP في سجلات دائمة فوق مدة تشغيل قصيرة (سياسة النشر).
- لا حذف خادمي فردي في v1 — الحذف عبر شاهد (tombstone) داخل الحالة المشفرة نفسها.

## خارطة التطبيق على العميل

```
SyncActivity  ──قراءة/كتابة──▶  المخازن الحقيقية (Theme/ClipRepo/Dictionary/Exceptions/Prefs)
      │                                   ▲
      ▼ collect/apply (SyncState)         │ applyPlan
  List<Rec> ──push/pull──▶ SyncClient (بوابة NetGate sync) ──▶ SyncRestTransport ──▶ هذا العقد
```

أي تغيير مستقبلي على هذا العقد يرفع رقم إصدار المسار (`/v2/…`) ويضيف قدرة جديدة في
NetGate — لا يغيّر `/v1/` تحت أقدام الإصدارات المنشورة.
