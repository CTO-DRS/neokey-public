# تقرير الأسبوع 3 من المرحلة 1 — البند A1: تنسيق النموذج العصبي + محرك الاستدلال النقي

**التاريخ:** 2026-11-02 · **الأسبوع الكلي:** 9 · **الإصدار:** vc56 (بلا رفع — لا تغيير في سلوك التطبيق بعد)

## 1. ما وعدته الخارطة لهذا الأسبوع

> «تنسيق أوزان ثنائي كمّي (int8) + محرك استدلال نقي Java (مضاعفة مصفوفات كمية) بلا أي مكتبة خارجية»
> **بوابة القبول:** «استدلال p50 < 8ms على JVM على نموذج اختباري، حجم التنسيق موثق»

## 2. ما سُلّم فعلاً

### NQF v1 — تنسيق نيو كيبورد الكمّي (`src/com/hark/neokey/NQF.java`، نقي 100%)

حاوية أوزان ثنائية ذاتية الوصف: ترويسة ثابتة 20 بايت + ميتا JSON + دليل موترات
(اسم/نوع/أبعاد/مقياس/إزاحة/طول/crc32) + كتل int8 خام + مقتبس CRC32 للملف كله.

- **int8 متماثل لكل موتر** للأوزان، **F32** للانحيازات وLayerNorm — ~1 بايت/معامل.
- **تغطية سلامة مزدوجة:** CRC للملف كله + CRC لكل موتر (يمكّن التحميل الكسول لاحقاً).
- **قارئ صارم** يرفض: السحر/الإصدار الخاطئ، البتر، انقلاب أي بايت (كتلة/ميتا/دليل)،
  تعارض الأبعاد مع طول البيانات، المقياس NaN/صفر، تداخل الكتل مع الدليل، البايتات
  الزائدة — **ولا يعيد أبداً نموذجاً ناقصاً**. كل قاعدة من العشر لها إثبات سلبي مكتوب.
- الكاتب نفسه يرفض 8 فئات من الأخطاء وقت البناء (تعارض الأبعاد، مقياس غير سالم،
  أسماء مكررة/فارغة، رتب خارج 1..6).

### NNet — محرك الاستدلال (`src/com/hark/neokey/NNet.java`، نقي 100%)

- **الضرب الكمّي الحقيقي:** تكميم ديناميكي للتنشيط (max|x|/127) → **int8×int8→int32**
  → إزالة الكمّ مرة واحدة بـ (wscale×ascale) + انحياز. لا مسار float في الضرب.
- **حرس الفيض بالتصميم:** ‏`MAX_COLS=32768` ⇒ ‏127²×32768 = 528M < 2³¹ — التجميع
  الصحيح لا يفيض أبداً؛ عرض أكبر = رفض بناء، لا نتيجة صامتة خاطئة.
- العمليات: `dynQuantScale` / `quantize` / `deqRow` / `matVecQ8` / `matVecF32` (مرجع
  الاختبار) / `layerNorm` (ε=1e-5) / `gelu` (تقريب tanh) / `relu` / `softmax` مستقر /
  `topK` (كسر التعادل بالفهرس الأدنى — حتمي عبر الأجهزة).
- **`NNet.Mlp`** — عقد نموذج التنبؤ بالكلمة التالية الذي يدرّب عليه A2: تضمين مشترك
  `emb` → دمج السياق → fc0 → LayerNorm → GELU → out → logits، بمخازن معاد
  استخدامها (صفر تخصيص لكل استدلال). يرفض أي نموذج بأبعاد غير متسقة **وقت التحميل**.

### بوابة `nnet` — المرحلة العاشرة في خط الإنتاج (`ci/nnet_gate.sh` + `NNetGate.java`)

1. يبني نموذج اختبار **حتمياً** بمقياس A2 (vocab 5000 / ctx 2 / emb 64 / hidden 256)،
   يكتبه NQF على القرص ويعيد قراءته (I/O حقيقي).
2. يقيس الاستدلال الكامل: **p50 < 8ms** (حد الخارطة) وp95 < 25ms على 200 سياق حتمي
   بعد 30 تسخيناً.
3. **حجم التنسيق موثق بالكود:** طول الملف يجب أن يساوي الحساب المرجعي بالبايت
   (`expectedBytes()`)، الفوقية < 2%، الملف < 8MB — وإلا `NNET_GATE_FAILED`.
4. يتحقق عددياً: `matVecQ8` مقابل ظل fp32 على طبقة الإخراج الحقيقية (< 3%).
5. **إثباتات سلبية:** خمسة تشويهات (سحر/إصدار/بتر/قلب بايت كتلة/قلب بايت ميتا) يجب
   أن يرفضها القارئ جميعها — أي قبول = فشل بوابة.

## 4. لماذا هذا الشكل بالذات (القرارات المعمارية)

1. **ملف واحد للتنسيق (NQF.java) لا مكتبة** — نفس الصنف يكتب ويقرأ ويُختبر؛ أي
   انحراف مستقبلي في A2 عن المواصفة يُكتشف ببوابة نفسها لا بمراجعة بشرية.
2. **الميتا JSON داخل الملف** — A2 يحتاج أن يحمل vocab وأبعاد الطبقات مع الأوزان؛
   التمديد الآن يمنع كسر الإصدار لاحقاً (القارئ v1 يقبل أي ميتا ويتجاهل الأعلام).
3. **CRC مزدوج لا CRC واحد** — مقتبس الملف يكشف أي تخريب موضعي فوراً؛ CRC الموتر
   يمكّن لاحقاً تحميل موتر واحد من ملف كبير بلا قراءة كاملة.
4. **int8×int8 لا weight-only** — نص الخارطة يقول «مضاعفة مصفوفات كمية»؛ التكميم
   الديناميكي للتنشيطات يعطي ذلك حرفياً، مع خطأ مقاس 0.27% فقط.
5. **topK حتمي بكسر تعادل الفهرس الأدنى** — تنبؤ الكلمة التالية يجب أن يكون نفسه
   على جهازين مختلفين لنفس المستخدم، وإلا فقدنا قابلية إعادة إنتاج القياسات.

## 5. بداية الحقائق التالية (الأسبوع 4 — A2: التدريب والقياس)

1. تدريب نموذج 1–3M معامل على نص عربي مفتوح وتصديره بهذا التنسيق — أي ملف لا
   يمر من `NQF.read` الصارم لا يُقبل مهما كانت دقته.
2. جسر التحميل داخل التطبيق (assets → `NQF.read` → `NNet.Mlp`) وإرجاع R8 لهما
   إلى dex — ثم قياس Top-3 ≥ 45% مقابل المسار التقليدي (قاموس + ثنائيات).
3. قياسات الجهاز الحقيقية (الهاتف المرجعي 2GB) — أرقام JVM هذه هي السقف النظري.
