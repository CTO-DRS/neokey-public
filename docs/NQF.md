# NQF v1 — تنسيق نيو كيبورد الكمّي للأوزان العصبية

> المرجع في خارطة الطريق — المرحلة 1، البند A: «نموذج عصبي مضغوط (Quantized)… كل هذا الذكاء يعمل محلياً بنماذج مضغوطة حجم كل منها بالميغابايتات لا بالغيغابايتات».
> البند A1 (الأسبوع 3): «تنسيق أوزان ثنائي كمّي (int8) + محرك استدلال نقي Java بلا أي مكتبة خارجية — استدلال p50 < 8ms على JVM على نموذج اختباري، حجم التنسيق موثق».

هذا الملف هو **المواصفة الرسمية** للتنسيق. الكود المرجعي الوحيد: `src/com/hark/neokey/NQF.java`
(الكاتب + القارئ الصارم) و`src/com/hark/neokey/NNet.java` (المحرك). لا مكتبات خارجية،
لا `android.*` — يُختبران على JVM كما يُشحنان تماماً.

## 1. لماذا int8 كمّي؟ (الحساب الهندسي)

| القرار | السبب المقاس |
|---|---|
| أوزان int8 متماثلة لكل موتر | ~1 بايت/معامل: نموذج A2 بـ 1–3M معامل = 1–3MB « 8MB (حد الخارطة) |
| تجميع int32 نقي في الضرب | الضرب الكمّي الحقيقي int8×int8→int32، ثم إزالة الكمّ مرة واحدة لكل عنصر إخراج |
| تكميم ديناميكي للتنشيطات (لكل موتر، عند الاستدلال) | بلا مرحلة معايرة إضافية عند التدريب؛ الخطأ المقاس 0.27% مقابل fp32 |
| حرس `MAX_COLS = 32768` | ‏127²×32768 = 528M < 2³¹ — التجميع الصحيح لا يفيض **بالتصميم** لا بالحظ |
| صفر NaN ممكن من مدخلات منتهية | متجه صفر → مقياس 1e-8 وليس قسمة على صفر؛ المقياس دائماً منتهٍ > 0 |

## 2. تخطيط الملف (كل الأعداد Little-Endian)

```
الإزاحة   الحجم        الحقل
0         4            السحر "NQF1"
4         2            الإصدار (u16 = 1)
6         2            الأعلام (u16، محجوز — الكاتب يكتب 0، القارئ يقبل أي قيمة)
8         4            عدد الموترات (u32 ≤ 65535)
12        4            حجم الدليل dirBytes (u32)
16        4            حجم الميتا metaLen (u32 ≤ 16MB، JSON UTF-8، يسمح 0)
20        metaLen      الميتا: JSON UTF-8 (وصف النموذج: ctx/emb/hidden/vocab/التدريب)
…         dirBytes     الدليل — لكل موتر:
                         u16 طول الاسم + الاسم (UTF-8)
                         u8 نوع البيانات (1 = Q8، 2 = F32)
                         u8 الرتبة (1..6)
                         الرتبة × u32 الأبعاد
                         f32 المقياس (Q8: القيمة = q × المقياس؛ F32: يكتب 1.0)
                         u32 إزاحة البيانات (مطلقة، داخل منطقة الكتل)
                         u32 طول البيانات بالبايت
                         u32 crc32 لبايتات الموتر الخام
…         متغير        كتل البيانات الخام (صف-رئيسي، أبعاد[0]×أبعاد[1]×…)
n−4       4            المقتبس: crc32 لكل البايتات [0, n−4)
```

**التغطية المزدوجة للسلامة:** كل بايت في الملف مغطى بـ CRC للمقتبس، وكل موتر مغطى
إضافةً بـ CRC خاص به (هذا ما يسمح لاحقاً بالتحميل الكسول لموتر واحد في الأسبوع A2+).
أي انقلاب بت واحد → رفض فوري، لا تنبؤ صامت خاطئ أبداً.

## 3. عقد الصرامة (كل قاعدة لها اختبار إثبات سلبي)

القارئ `NQF.read()` يرمي `NQF.BadFormat` — ولا يعيد أبداً نموذجاً ناقصاً — عند:

| # | القاعدة | الاختبار |
|---|---|---|
| 1 | سحر `NQF1` وإصدار 1 بالضبط | NNetTest «bad magic/version refused»، NNetGate «magic/version» |
| 2 | عدد الموترات ≤ 65535، الميتا ≤ 16MB | نفي «tiny bytes» + حرس ميتا |
| 3 | أسماء غير فارغة وفريدة | «empty/duplicate name refused» (كاتب + قارئ) |
| 4 | dtype ∈ {1,2}، الرتبة 1..6 | «rank 0/7 refused» |
| 5 | حاصل ضرب الأبعاد (كـ long) = طول البيانات (Q8) أو طولها÷4 (F32) | «dims/product mismatch refused» |
| 6 | حاصل الضرب يتسع لمصفوفة Java؛ مقياس Q8 منتهٍ > 0 | «NaN scale refused» |
| 7 | الكتل بعد الدليل حصراً وداخل [0, n−4) | «blob overruns/overlaps» في القارئ |
| 8 | crc32 لكل موتر + crc32 للمقتبس | «one flipped byte refused» (كتلة، ميتا، عدّاد موترات) |
| 9 | الدليل يُستهلك بالضبط — لا بايتات زائدة | «directory slack» في القارئ |
| 10 | الكاتب نفسه يرفض: تعارض الأبعاد/البيانات، مقياس 0/NaN/∞، اسم مكرر/فارغ، رتبة خارج 1..6 | 8 اختبارات كاتب في NNetTest |

## 4. عقد أسماء الموترات (واجهة النموذج العامة — يدرّب عليها A2)

| الاسم | الأبعاد | النوع | الدور |
|---|---|---|---|
| `emb` | vocab × embDim | Q8 | تضمين الرموز المشترك |
| `fc0.w` | hidden × ctx·embDim | Q8 | الطبقة الكثيفة الأولى |
| `fc0.b` | hidden | F32 | انحياز الأولى |
| `ln.g` / `ln.b` | hidden | F32 | LayerNorm بعد fc0 (اختياري — يجب القدوم معاً) |
| `out.w` | vocab × hidden | Q8 | طبقة الإخراج |
| `out.b` | vocab | F32 | انحياز الإخراج |

مسار الاستدلال في `NNet.Mlp.forward(ctx ids)`:

```
concat(deq(emb[id]) لكل سياق) → تكميم ديناميكي → matVecQ8(fc0) → LayerNorm → GELU
                            → تكميم ديناميكي → matVecQ8(out) → logits → topK(k)
```

`Mlp` يرفض البناء على أي نموذج بأبعاد غير متسقة (fc0.w لا يطابق ctx·embDim، انحيازات
بحجم خاطئ، ln.g دون ln.b…) — عقد A2 يُفرض وقت التحميل لا وقت الفشل.

## 5. حجم التنسيق — موثق بالكود لا بالكلام

بوابة `NNetGate` تُحاسب الملف بايت-بايت وتفشل البناء إذا اختلفت الحسبة:

| القياس | القيمة المقاسة (نموذج البوابة: vocab 5000 / ctx 2 / emb 64 / hidden 256) |
|---|---|
| معاملات Q8 | 1,632,768 (الحد المثالي = بايت لكل معامل) |
| معاملات F32 | 6,024 (انحيازات + LayerNorm) |
| حجم الملف | **1,656,261 بايت ≈ 1.58MB** — مقابل حد 8MB |
| الفوقية فوق 1 بايت/معامل | **1.44%** (ترويسة + دليل + ميتا + مقتبس؛ البوابة ترفض > 2%) |
| بت/معامل Q8 فعلياً | 8.115 |

## 6. نتائج البوابة (بيئة JVM هذه — أرقام الجهاز تأتي في A2)

```
NNETGATE model_params=1638792 (q8=1632768 f32=6024) model_bytes=1656261
          overhead=1.44% bpp=8.115 p50=0.641ms p95=0.705ms matvec_err=0.0027
          negatives=[magicOK, versionOK, truncationOK, blob-flipOK, meta-flipOK]
```

- **p50 = 0.641ms** على نموذج بـ 1.64M معامل — 12× هامش تحت حد الخارطة 8ms.
- الخطأ الكمّي مقابل fp32 على طبقة الإخراج الحقيقية: 0.27%.
- القرارية حتمية: نفس الأوزان + نفس المدخل = نفس اللوجتس بت-بت (لا HashIteration
  في أي مسار رقمي، لا تفرّع عشوائي).

## 7. ما بعدها (الأسبوع A2 — «التدريب والقياس»)

1. تدريب نموذج 1–3M معامل على نص عربي مفتوح، وتصديره **بهذا التنسيق حرفياً** —
   أي نموذج لا يقرأه `NQF.read` الصارم لا يُقبل.
2. جسر Android للتحميل (Assets → NQF.read → Mlp) وتفويض NNAPI لاحقاً على الأجهزة
   الحديثة مع التراجع لهذا المسار.
3. القياس: Top-3 ≥ 45% مقابل المسار التقليدي — مقاساً لا مزعوماً.

ملاحظة R8 (أسبوع A1): `NQF`/`NNet` غير مرتبطين بعد بأي مسار من الـ Manifest، لذا
يزيلهما R8 بالكامل — dex بقي 440,340 بايت كما في الأسبوع 8 حرفياً. هذا هو السلوك
الصحيح: صفر بايت تكلفة حتى توصيل A2، ويُثبت غيابهما في mapping.txt.
