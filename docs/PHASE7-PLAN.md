# خطة المرحلة 7 — «من المُشحَّن إلى المُشغِّل» (اشتقاق موثق لا افتراض)

قاعدة الاشتقاق هي قاعدة المراحل 3 و4 و5 و6 نفسها: **المرحلة القادمة تُشتق من
المعلقات الموثقة كتابةً داخل مشروع المرحلة السابقة، لا من افتراض خارجي.**
مصدر الاشتقاق هنا: `docs/PHASE6-W4-REPORT.md` §7 (نص المعلقات عند إغلاق
المرحلة 6) و`store-readiness.pendingOutsideThisEnvironment` بنصها الخمسة.

## المعلقات الموثقة التي اشتُقت منها (نصها الأصلي في
## `store-readiness.pendingOutsideThisEnvironment` بعد إغلاق المرحلة 6)

1. **«real payment provider (Play Billing) — replaces
   `PaymentProvider.SimProvider` in `StoreActivity` only»** — عقد الدفع
   نقطة استبدال قياسية منذ الأسبوع 24 (إيصال مختوم حتمي، المحفظة تتحقق
   بإعادة اشتقاق الختم لا بثقة، والسقوف محفظية قبل المزوّد)؛ الشريحة
   المحلية القابلة للإغلاق الباقية هي **إثبات الاستبدال نفسه قبل وجود
   الحساب**:
   - **W1 (الأسبوع 34): مُحوّل الفاتورة المُثبَت** —
     `PaymentProvider.PlayProvider`: مُحوّل نقي-JVM على شكل مسار Play
     Billing الفعلي (استعلام المنتج ← شراء ← acknowledge) يستلم من نقطة
     الوصل (الواجهة الوظيفية التي سيغذّيها `BillingClient` لاحقاً) سجل
     الشراء الخام `purchaseJson` + توقيعه `signature` **ويُحقق قبل أن
     يعيِن أي إيصال**: توقيع RSA/SHA256 بمفتاح اللوحة العام («المرجع =
     المنشور» — نفس قانون الدبوس والختم: لا ثقة، تحقق)، حالة الشراء
     `purchased`، المنتج في فهرس الأسعار، وربط الطلب
     `obfuscatedExternalAccountId == requestId`؛ ثم يختم الإيصال
     **بالاشتقاق نفسه** `Receipt.sealed(id(), requestId, cents,
     externalRef=orderId)` — فالمحفظة وجرنتها لا تعرفان أن المزوّد تغيّر.
     **تعادل العقد:** جناح اختبار العقد نفسه يجري على `SimProvider`
     وعلى `PlayProvider` (بمفاتيح RSA اختبارية تولَّد زمن الاختبار) ويعطي
     النتائج ذاتها — فالاستبدال سطر واحد مُثبَت، وما يبقى خارج البيئة:
     سلك `BillingClient` (يحتاج جهازاً) + مفتاح اللوحة الحقيقي.
2. **«live sync server deployment with TLS on a real domain … running the
   two automated commands»** — القرار آلي عضّال (W1/30) والأمران آليان؛
   الشريحة المحلية الباقية هي **الأرتقف القابل للتشغيل ذاته**:
   - **W2 (الأسبوع 35): خادم المزامنة أرتقف نشر** — jar قابل للتشغيل +
     سكربتات تشغيل/إيقاف + فحص صحة ذاتي + وثيقة تركيب أوامرها سطور
     نسخ-لصق حرفية (منها الأمران)؛ بوابة تُقِم الخادم محلياً على
     `127.0.0.1` وتجري جولة سلك كاملة على الأرتقف المُشغَّل — فيُثبَت أن
     ما سيُنشر هو الأرتقف المُختبر ذاته. ما يبقى خارج البيئة: النطاق +
     شهادة CA + تشغيل الأمرين.
3. **«store developer accounts + the upload click itself»** — الحزمة
   مجمّعة ومتحقق منها منذ W3/32؛ الشريحة المحلية الباقية عبر المرحلة كلها
   هي **إبقاء كل خطوة مشغِّل إما مُفحوصة هنا أو خارجية بأمرها الحرفي**:
   - **W3 (الأسبوع 36): الفحص التمهيدي للمشغِّل** — أداة `Preflight`
     واحدة تمشي على شروط النشر كلها بفحوص محلية حتمية: إعادة تحقق حزمة
     الرفع، إعادة تشغيل تدريب استعادة المخزن، جناح عقد المُحوّلين، إقامة
     الخادم وجولة سلك، وجود أوامر الإصدار — وتُصدر ورقة التسليم: كل خطوة
     إما `CHECKED` هنا أو `OUTSIDE` بأمرها الحرفي وخارجيتها الموثقة.
4. **«keystore secrets restore … the actual restore stays with the
   owner»** — النصفان مُثبتان (W3/28 + W2/31)؛ لا شريحة محلية جديدة —
   يُحرس بالفحص التمهيدي (W3) أن إجراء W28 يظل يعضّ في كل تشغيل لاحق.
5. **«real-device matrix + MAU numbers»** — خارجي بالكامل (جهاز + حساب)؛
   لا شريحة محلية — يوثَّق في ورقة التسليم (W3) كما هو، بلا تظاهر.

## قوانين لا تُكسر (موروثة حرفياً)

- سقف dex = **512,000B** مخفَّض؛ الفيضان يعني تقليماً لا رفعاً.
- **المرجع = المنشور** في كل مرساة (دبوس، بصمة، توقيع شراء): الحرفية لا
  الاتساق الداخلي.
- **الإثبات السلبي المحفوظ إلزامي** لكل بوابة أسبوع، ونسخه في
  `ci/<gate>-negative-proof.log`.
- الاتساق الثلاثي للأدلة: طازج == pipeline.log == gates.env، والحقول غير
  الحتمية (زمن، ms، صلاحية متآكلة) **حدود لا مساواة**.
- أسبوع الإغلاق لا يكتب dex جديداً؛ هوية الأسبوع تتحرك في مواضعها الخمسة
  معاً (المانيفست + حرفا `EXPECTED` في بوابتي الأرتقف + تأكيدا الهوية
  الحية في اختبار الحزمة) — وأي حركة ناقصة يصطادها الأنبوب من أول تشغيل.
